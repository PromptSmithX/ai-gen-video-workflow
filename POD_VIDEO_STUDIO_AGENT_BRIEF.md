# POD Video Studio — Implementation Brief for Multi-Agent Coding

**Document type:** Product + engineering brief / build instructions  
**Target:** Windows desktop application, distributed internally as one company installer (`.exe`)  
**Primary workflow:** Employee uploads one product mockup → selects SKU/template → app sends the source image and a generated prompt to the company's Muse bridge → the existing Muse video generator creates the video → app downloads and stores the MP4 under the SKU.  
**Review date:** 2026-11-23

---

## 0. Instructions to the coding agents

You are a multi-agent engineering team implementing **POD Video Studio** inside the company's existing repository.

Do not start by writing UI code. First inspect the current repository, identify its framework, conventions, build pipeline, tests, data layer and existing security controls. Reuse the existing stack where sensible. Do not replace working infrastructure without a concrete reason.

### Non-negotiable constraints

1. **The production video must be generated by the same Muse video generator that the employees currently use.** Do not silently substitute Runway, Kling, Seedance, a Meta Model API, or another video provider.
2. Do not assume a public Muse video-generation API exists. The reference repository reviewed for this brief exposes a local REST façade, but its internals automate a web session; that is not the same as an official provider API.
3. Do not clone, vendor, download, install or execute the third-party `andrew-babo/muse4ai` repository or its installer as part of this task.
4. **Do not copy code from that repository in this first implementation.** Learn from its module boundaries, API shape, data model and test strategy. Reimplement the company's own product-specific code in our repository. If the team later proposes copying any source, stop and produce a separate license/provenance review first. Preserve required MIT notices for any approved copied portions.
5. No reverse-engineering intended to bypass authentication, paywalls, rate limits, anti-bot controls, CAPTCHA, safety refusals or other access controls. No cookie export/import, password scraping, hidden credential capture, session theft or account sharing. Authentication must be performed by the employee through the normal provider login flow, if this integration is permitted.
6. The app must not automatically retry a generation after it may already have been submitted. Resolve ambiguous submit status before any retry to prevent duplicate video jobs and wasted quota.
7. Do not log prompt contents, image bytes, authentication cookies, bearer keys, access tokens, session identifiers or signed download URLs.
8. All network listeners must bind to `127.0.0.1` by default. No LAN listener, public tunnel, reverse proxy or cloud relay in MVP.
9. Treat source mockups and generated videos as company data. Store them only in approved local or company storage locations.
10. Do not claim the integration is officially supported by Muse or its provider. Obtain internal legal/product approval against the provider's current Terms before production rollout.

### Critical platform compatibility gate

The reviewed reference repository hard-codes the provider origin `https://muse.ai/` in `desktop/src/main/adapter/muse/selectors.ts`. It also uses page selectors, a session endpoint, browser upload interactions and page-state parsing. That does **not** prove compatibility with any other product that happens to be called “Muse”.

Before implementation, inspect the actual Muse product URL employees use and record its exact origin in `docs/integration/platform-compatibility.md`. If it is not `https://muse.ai`, mark the reference repository's automation adapter **not compatible** until a legitimate integration method for the actual product is established. Do not copy the `muse.ai` selectors or endpoints and assume they work against another domain.

If the provider does not permit this kind of automation, stop the provider-integration work and report the blocker. Continue only with the independent POD UI, prompt library, SKU library and media-management components.

## 1. Product goal

Build a Windows app so a non-technical employee can:

1. Open **POD Video Studio**.
2. Drag one product mockup image into the window.
3. Enter or select the SKU.
4. Choose a product category and video template.
5. Preview and optionally edit the final prompt.
6. Click **Generate video**.
7. See generation progress, preview the final video and save it automatically.

The employee should not need to open Muse manually for every job, learn prompt engineering, understand API calls or manage files by hand. The employee must still complete any provider login/consent step required by the provider and the bridge.

### Product principles

- The uploaded product image is the single source of truth for product appearance.
- Preserve the artwork exactly: typography, logos, illustrations, layout, colors, placement and small details must not be redesigned or replaced.
- The prompt may add a natural product-review scene, camera work, hands/person/environment and lighting, but it must not authorize changes to the actual design printed on the product.
- Product realism matters: natural material texture, believable folds and weight, realistic skin, physically plausible handling and consistent front/back orientation.
- Avoid a “zoom-only” output. Use a review-oriented template that requests meaningful product interaction, with physically continuous action and no impossible object transformations.
- Do not hard-code a rigid frame-by-frame storyboard as the only prompt style. Keep the current Prompt Master editable and versioned.
- One uploaded mockup normally creates one video. Multi-video/repeat generation is a future feature and must be explicitly user-selected.

## 2. Reference repository review — Muse4AI

Reference: [andrew-babo/muse4ai](https://github.com/andrew-babo/muse4ai)  
Reviewed default branch: `main`  
Reviewed commit: [`c661f83b8e7883e6fb1f16e1b584284818b26b29`](https://github.com/andrew-babo/muse4ai/commit/c661f83b8e7883e6fb1f16e1b584284818b26b29)  
Repository `package.json` version observed: `2.0.0-beta.35`  
Repository license observed: MIT.

### 2.1 What the reference project actually does

It is not merely a web form calling a documented official video API. It is a sizeable Electron desktop app with:

- A local React/Electron UI.
- A main process that owns the database and business logic.
- Persistent per-account Electron browser sessions.
- A Muse-specific adapter containing page URLs, selectors, upload logic, prompt submission and result observation.
- A job coordinator/queue and account-aware scheduler.
- A local REST/MCP/OAuth façade for external agents.
- SQLite persistence for jobs, references, assets, accounts, API keys, request logs and related state.
- A vault for secrets, installer and updater components, Windows integration and a large test suite.

Its README documents a local API on `http://127.0.0.1:47821`, with `GET /v1/status`, `POST /v1/references`, `POST /v1/jobs`, `GET /v1/jobs/{id}` and asset-download endpoints. Those are endpoints of **Muse4AI**, not official provider endpoints.

The project also contains a “Direct channel” implementation described in `desktop/AGENTS.md`. Therefore do not assume all requests are performed by the same UI-only mechanism. The internal adapter and scheduler are more complex than the README's simple REST example suggests.

### 2.2 Architecture worth learning from (do not copy blindly)

| Reference area | What is worth learning | Our intended adaptation |
|---|---|---|
| `desktop/src/main/` | Main-process ownership of state and privileged operations | Keep filesystem, provider bridge, tokens and database out of renderer/UI code |
| `desktop/src/renderer/` | UI separated from main process | Build a simple employee workflow and live job status |
| `desktop/src/main/adapter/muse/` | Provider-specific knowledge isolated in one adapter | Create a narrow `MuseProvider` interface; keep all provider-specific integration behind it |
| `desktop/src/main/coordinator.ts` and services | One coordinator owns submissions and job state | Use one job orchestrator; avoid creating duplicate jobs from concurrent clicks/retries |
| `desktop/src/main/api/` | Local REST façade, auth, schemas, idempotency, rate limits | Use a small typed local IPC/API boundary only where required |
| `desktop/src/main/repo.ts`, `db.ts` | SQLite persistence and migrations | Persist SKU/job metadata locally; keep outputs in a filesystem/NAS media library |
| `desktop/src/main/vault.ts` | Central secret-storage abstraction | Use Windows DPAPI/Credential Manager; **fail closed** if encryption is unavailable |
| `desktop/test/` | Unit/integration tests and test harnesses | Mock the Muse bridge; do not call live provider from normal CI |
| `desktop/installer/` and `scripts/` | Windows install, update, rollback and hash checks | Build a signed company installer with verified artifacts and safe rollback |
| `content/`, `agent-kit/` | Shared docs/templates kept in one source | Keep Prompt Master versions and employee guidance in one canonical location |

The review was based on source files read through GitHub's repository integration, without cloning, building, installing or executing the project. Files inspected included:

- `desktop/src/main/api/server.ts`, `controller.ts`, `service.ts`, `store.ts`, `childProc.ts`, `tunnel.ts`, `caddy.ts`, `updater.ts`.
- `desktop/src/main/adapter/muse/driver.ts`, `selectors.ts`.
- `desktop/src/shared/api/schemas.ts`, `openapi.ts`, `keys.ts`, `netPolicy.ts`, `constants.ts`, `validate.ts`.
- `desktop/installer/install.ps1`, `desktop/installer/setup.iss` and relevant tests.

**Result: no obvious malicious payload or credential-exfiltration routine was identified in the inspected code paths. This is not a malware-free certification.** A full repository scan, dependency/SBOM scan on the exact commit, binary scan, dynamic sandbox run, release artifact verification and full history review were not performed. Do not install or run the upstream binary on employee machines based only on stars or this source review.

#### Positive security signals observed

- The repository has an MIT license and a `SECURITY.md` responsible-disclosure policy.
- `README.md` describes a CI audit process including tests, type checking, dependency checks and secret scanning. `.github/workflows/audit.yml` shows tests/typecheck, `npm audit` and Gitleaks checks.
- `ApiServer` has authenticated routes, request-size limits, rate limiting, host validation and rejects cross-origin browser requests/OPTIONS. Its test suite includes checks for loopback-only binding and Origin/Host rejection.
- The API is documented as off by default. When enabled in local mode, the controller binds to `127.0.0.1`; LAN and Cloudflare tunnel modes are separate explicit settings.
- API keys are generated using cryptographic random bytes. The shared key implementation hashes tokens with SHA-256, and the store keeps the digest rather than the raw key.
- The Electron windows inspected use `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false` and `webSecurity: true`.
- The code centralizes most state in the main process and uses SQLite with parameterized queries in inspected repository methods.
- Downloaded helper binaries and app updates have pinned hash/size verification paths in the inspected code.
- The Muse driver deliberately avoids some dangerous retry behavior: after an uncertain send it classifies the state as ambiguous instead of blindly resending.

#### Risks and unresolved questions

1. **Provider/ToS risk:** The reference README explicitly warns that it automates a web app and may not fit the provider's Terms. The adapter uses private/version-sensitive page details. This is a production blocker until the company's intended use is checked against current provider terms and approved.
2. **Compatibility risk:** The adapter hard-codes `https://muse.ai`, `/api/session`, `/api/auth/check`, `/api/hatch/vm/wake` and CSS/data-testid selectors. These are not documented public API contracts and can break without notice. They may not match the Muse app used by this company.
3. **Vault fallback:** `desktop/src/main/vault.ts` stores secrets as `plain:<base64>` when the OS encryption provider is unavailable. Base64 is not encryption. Our app must never copy this fallback. Fail closed and do not save provider secrets without DPAPI/Credential Manager.
4. **Updater trust:** The README says the Windows installer is unsigned and may trigger a Windows warning. The updater verifies SHA-256 against a manifest downloaded from the same publisher domain. This is useful for corruption/tampering detection but is not equivalent to a publisher signature rooted in a separate trust chain. Do not download or run the upstream installer for this project.
5. **Outbound network requests:** The inspected Muse selectors include `https://ipinfo.io/json` for public/exit-IP checking. Optional Cloudflare tunnel/Caddy components also exist. The README says there is no cloud middleman, but that should not be interpreted as “no third-party network traffic in every configuration.” Our MVP should have no public tunnel and should document every outbound host.
6. **Large attack surface:** The repository is much larger than the narrow POD workflow needs. It includes account/proxy management, MCP, OAuth, tunnels, Caddy, video extension, update/rollback and other features. Porting the whole application would unnecessarily expand attack surface and maintenance burden.
7. **Audit freshness:** The detailed audit file inspected is dated 2026-11-06 and describes beta.32 with 774 tests; the current `package.json` observed is beta.35 and README advertises 848 tests. Treat the detailed audit as historical, not proof that beta.35 or a release binary has passed the same checks. Run fresh checks at the exact reviewed commit.
8. **Workflow supply chain:** The audit workflow uses major-version GitHub Actions tags and downloads Gitleaks via `curl`/`tar`. For our own CI, pin third-party actions by full commit SHA and verify scanner downloads/checksums.
9. **Installer scripts:** The Windows installer invokes PowerShell with `-ExecutionPolicy Bypass`. This may be a legitimate installer technique, but scripts must be reviewed in full and never executed from an untrusted release during the initial review.
10. **No dynamic scan performed:** Static inspection cannot establish that the packaged binary, dependencies or runtime behavior are safe. A “~600 stars” reputation signal is not a security control and can never replace this review.

The root project declares MIT. The adapter also records MIT notices for code adapted from separate `muse2api` projects. MIT generally permits commercial reuse if its copyright/license notice requirements are followed, but the team must still track provenance for each copied file and must not assume an open-source code license grants permission to automate the provider's service. For this task, **do not copy source code**; use architectural lessons only.

## 4. Integration contract — reference Muse4AI local REST API

This section is an integration target for a separately approved local bridge. It is **not an official Muse provider API**. The reference repository README and `desktop/src/main/api/server.ts`, `service.ts`, `schemas.ts` and `openapi.ts` describe the following pattern.

### 4.1 Connection check

Base URL documented by the reference README:

```text
http://127.0.0.1:47821
```

- `GET /v1/health` — public health response.
- `GET /v1/openapi.json` — public API schema.
- `GET /v1/status` — requires bearer API key; contains app/provider status and capabilities.

Do not assume the port is always 47821. Discover it using an explicit app setting or approved bridge health/discovery mechanism. Do not scan arbitrary ports.

### 4.2 Upload the source mockup

Reference endpoint:

```http
POST /v1/references
Authorization: Bearer <LOCAL_BRIDGE_API_KEY>
Content-Type: image/png
X-File-Name: TS-001-mockup.png

<raw image bytes>
```

The source code reads raw file bytes. It does not expect JSON/base64 for this route. The response includes a `reference_id`, `kind`, MIME, dimensions, byte size and SHA-256. Store only the provider reference ID in the job record; keep the original file under the company's SKU media library.

Reference limits observed in source:

- `POST /v1/references` upload cap: 20 MiB.
- Images accepted by the media validator: PNG, JPEG and WEBP.
- The reference implementation validates the real file signature/MIME rather than trusting extension alone.

Our app should apply stricter UI limits if necessary (e.g. 15 MiB and max pixel edge), while preserving the source artwork. Do not silently redraw, recompress with lossy settings or crop the uploaded design. If normalization is required for size, keep the original and use a lossless derivative.

### 4.3 Submit image-to-video job

The reference schema supports `kind: "video"`, prompt, `mode: "reference"` and a `reference_id`. The request pattern is:

```http
POST /v1/jobs
Authorization: Bearer <LOCAL_BRIDGE_API_KEY>
Content-Type: application/json
Idempotency-Key: <stable-request-uuid>

{
  "kind": "video",
  "mode": "reference",
  "prompt": "<fully rendered Prompt Master>",
  "reference_id": "<ID returned by POST /v1/references>",
  "repeat": 1,
  "account": "auto"
}
```

The documented response is asynchronous (HTTP 202) and returns one or more job records. The local bridge schema caps the prompt at 4,000 characters in the video/image request schema. Confirm exact field names and response schema by reading that bridge's live `/v1/openapi.json` before integration; the OpenAPI document is the implementation contract.

Use a stable idempotency key derived from the internal job ID. Do not create a new idempotency key for an ordinary network retry.

### 4.4 Poll and download

- Poll `GET /v1/jobs/{id}` at a measured interval (e.g. 2–5 seconds with backoff); use any supported wait/long-poll option only after reading the exact OpenAPI schema.
- Map provider states into our own state machine.
- On `succeeded`, inspect the returned output metadata and download URL.
- Download to a temporary `.part` file, enforce a maximum size, validate MP4/container signature, compute SHA-256 and then atomically rename into the SKU folder.
- Do not accept a URL from a provider response without validating scheme/host against the approved local bridge contract. Prefer the authenticated local asset endpoint or an explicitly documented signed URL.
- Keep the provider job ID and asset ID in metadata, but do not expose private remote thread/session IDs in the UI or logs.

### 4.5 Error handling

Create explicit states and error codes:

- `NOT_CONNECTED` — local bridge is not running or health check failed.
- `NEEDS_LOGIN` — employee must sign in through the normal provider UI.
- `UNSUPPORTED_PLATFORM` — actual Muse host does not match the approved adapter.
- `QUOTA_LIMITED` — provider reports quota/credit limit; stop, show message, do not loop.
- `CONTENT_REFUSED` — provider refused; show safe message, do not rewrite artwork to evade the refusal.
- `PROVIDER_ERROR` — provider/service technical failure; allow one manual retry after user acknowledgement.
- `SUBMIT_AMBIGUOUS` — request may have been sent, but acceptance/result cannot be confirmed; do not resubmit automatically.
- `OUTPUT_MISSING` — provider marked job complete but no MP4 was delivered.
- `DOWNLOAD_FAILED` — generation completed, but the file could not be downloaded/validated.

Only retry failures known to have happened **before** the provider accepted the generation request. Never infer that a timeout means the provider did not receive the job.

## 6. Prompt Master and template system

Do not hard-code one giant prompt inside a UI component. Store templates as versioned files/configurations, e.g.:

```text
prompts/
  master/
    product-review-v1.md
    product-review-v2.md
  categories/
    apparel.md
    drinkware.md
    home-decor.md
  schema.json
```

The actual company-approved Prompt Master V2 text must be imported from the company's existing source. Do not invent or replace the current master prompt. Until that text is supplied in the repository, use a clearly marked placeholder and make the prompt editor visible in the admin/developer environment.

### Template variables

Support typed variables, validated before rendering:

- `{{sku}}`
- `{{product_category}}`
- `{{product_name}}`
- `{{source_image_filename}}` (metadata only; never pass local path to provider)
- `{{duration_seconds}}` (only where provider supports it)
- `{{aspect_ratio}}` (only where provider supports it)
- `{{review_style}}`

Never inject untrusted file names or arbitrary metadata as executable/template syntax. Escape values and keep unknown placeholders as a validation error.

### Prompt quality checks

Before submission, validate that the final prompt includes the company rules:

- Keep the exact uploaded design/artwork and printed text.
- Do not invent, simplify, replace, mirror, distort, recolor or reposition artwork.
- Keep the product identity and garment/product construction consistent throughout the video.
- Make hands/skin/material texture natural and non-plastic.
- Require physically continuous movement, gravity, folds and object permanence.
- Avoid impossible transitions (object suddenly worn, object turns into another side, product teleports, hand passes through object).
- Request a believable human product review, not only a slow zoom/pan across the still image.
- Do not add fake ratings, discounts, claims, testimonials or platform badges unless specifically supplied and approved.

Show prompt character count. If the chosen bridge has a 4,000-character limit, validate against that limit before submission.

## 8. Job orchestration and state machine

Use one authoritative coordinator in the main process. The renderer sends commands and receives read-only state snapshots/events.

```text
DRAFT
  ↓ validate image/SKU/template/connection
READY
  ↓ persist job + idempotency key
QUEUED
  ↓ reserve single-flight slot
SUBMITTING
  ├─ provider acceptance confirmed → RUNNING
  ├─ definitely not submitted → FAILED_RETRYABLE
  └─ uncertain whether accepted → AMBIGUOUS (no automatic resubmit)
RUNNING
  ├─ provider returns MP4 → DOWNLOADING
  ├─ provider refusal → FAILED_REFUSED
  ├─ quota → FAILED_QUOTA
  └─ provider technical error → FAILED_PROVIDER
DOWNLOADING
  ├─ validated file saved → SUCCEEDED
  └─ missing/corrupt/network failure → DOWNLOAD_FAILED
```

Rules:

- Persist `SUBMITTING`/submit intent before making the network call.
- Generate a stable UUID `requestId` per internal job and use it as idempotency key if supported.
- Only one submission per button click.
- Poll one provider job ID; do not create a new job during polling.
- A user-requested regenerate creates a new internal job and new idempotency key.
- A restart restores pending jobs and reconciles provider status where possible.
- Use bounded exponential backoff for status polling; never hammer the provider.
- Respect provider-reported quotas and concurrency. Default to one concurrent Muse generation per employee account until measured and approved otherwise.
- If the provider does not expose progress, show indeterminate progress and honest status labels; do not fabricate a percentage.

## 9. Security and privacy requirements

### Local network boundary

- Local bridge/base URL must be loopback-only (`127.0.0.1` / `localhost`) in MVP.
- Do not bind to `0.0.0.0`, `::`, a LAN IP or public address.
- Do not add Cloudflare tunnels, Caddy, ngrok or equivalent.
- Validate the local bridge's Host/Origin/auth requirements. Disable CORS rather than broad `*` CORS.
- Keep the bridge API key in Windows Credential Manager or DPAPI-protected storage. Never place it in renderer localStorage, config JSON, logs, environment diagnostics or installer command lines.
- Do not store provider cookies or reuse the browser profile from another employee.

### Secrets and session handling

- Use OS-backed encryption only. If DPAPI/Credential Manager is unavailable, refuse to persist the secret and show a setup error. **No base64/plaintext fallback.**
- Do not ask employees to paste their Muse password into POD Video Studio.
- If a provider login window is required, use the approved provider sign-in flow and a dedicated, per-user profile. No cookie reading/export.
- Never share one employee's logged-in session with another employee.
- Provide disconnect/sign-out/clear-local-session controls according to the provider's supported flow.

### File handling

- Allowlist image extensions and validate file signatures and dimensions.
- Cap source file size and image pixel count to avoid decompression bombs/memory exhaustion.
- Write to a temp directory with restrictive user permissions; atomically move only validated files to the library.
- Validate downloaded video signature/container, byte count and SHA-256. Do not execute provider output.
- Block path traversal, symlinks/reparse-point escape and arbitrary output paths.
- Never auto-open downloaded files.

### Logging and diagnostics

- Structured logs with correlation ID, internal job ID, SKU, status, duration and safe error code.
- Redact API keys, access tokens, cookies, session IDs, prompt body, signed URLs and raw file paths where sensitive.
- Diagnostics export must be opt-in and previewable before export.
- Set retention (e.g. 14–30 days) and allow admin cleanup.

### Updates and supply chain

- Build artifacts in controlled CI.
- Pin dependencies and lockfile; run SCA/SBOM and secret scanning.
- Pin GitHub Actions by full commit SHA.
- Sign Windows installers and executables with the company's code-signing certificate.
- Verify release signatures and SHA-256 before update installation.
- Never run arbitrary PowerShell downloaded from a remote source.
- Provide rollback and preserve user data during update/uninstall.

## 10. Testing plan

### Unit tests

- SKU normalization and path-safety.
- File signature/MIME validation, file size and image-dimension limits.
- Prompt template rendering, unknown variable rejection and max prompt length.
- Job state transitions and ambiguous-submit semantics.
- Idempotency: duplicate request ID returns the existing job, not a second provider generation.
- Asset SHA-256 and MP4 signature validation.
- Secret redaction.
- SQLite migration and backup/restore.

### Integration tests with mocked provider

- Health check not reachable.
- Login required.
- Upload source image then submit one video job.
- Job queued/running/succeeded.
- Refusal, quota exhausted and provider 5xx.
- Network interruption before submit.
- Network interruption after submit (must become ambiguous, not auto-resubmit).
- Provider returns success but no asset.
- Download truncated/corrupt MP4.
- Cancel behavior only if provider capability genuinely supports cancel.

### Windows E2E

- Fresh install for standard user (no admin rights if possible).
- First-run onboarding and provider connection.
- Drag/drop PNG, JPG and WEBP.
- One-click generation and video preview.
- App restart while a job is running; reconcile safely.
- Reinstall/update/uninstall preserves library and database.
- Multi-user Windows machine does not mix user profiles/session data.
- Installer and executable show valid company signature.

### Security tests

- Local API is unreachable from other LAN devices.
- No wildcard CORS.
- Unauthorized API calls rejected.
- API key never appears in logs/config/renderer state.
- DPAPI unavailable → no plaintext fallback.
- Malicious SKU/path traversal rejected.
- Oversized and malformed image rejected.
- Arbitrary provider result URL rejected.
- Diagnostics contain no token/cookie/prompt/image content.

No normal test or CI job may submit real provider generations or spend employee quota.

## 12. Definition of Done for MVP

The MVP is complete only when all of the following are true:

- [ ] It installs as one company-branded Windows installer.
- [ ] Employee can upload one source mockup, enter SKU and select a versioned Prompt Master.
- [ ] Prompt preview is visible and validates the company artwork-preservation rules.
- [ ] The exact existing Muse video generator is used; there is no silent provider substitution.
- [ ] Provider compatibility and permitted integration method are documented and approved.
- [ ] One click creates at most one provider generation.
- [ ] Ambiguous submit never causes an automatic duplicate generation.
- [ ] Successful MP4 is validated, hashed and stored under the correct SKU.
- [ ] Job and asset metadata survive application restart.
- [ ] UI exposes safe, understandable states/errors.
- [ ] No secret is stored in plaintext or written to logs.
- [ ] Local network API is loopback-only and authenticated.
- [ ] Tests pass on the exact release commit; security scan/SBOM report is attached.
- [ ] Installer and executable are signed by the company.
- [ ] Pilot has been tested on one isolated Windows PC before company-wide rollout.
